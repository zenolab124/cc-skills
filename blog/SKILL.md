## 第零阶段：预检查（必做，跳过会出错）

写任何东西之前，先确认事实而不是依赖记忆：

1. `ls /Users/xt/workspace/blog/src/content/posts/ | tail -5` — 确认目录存在并看到最近的文章命名风格
2. **读 schema 文件** [src/content.config.ts](file:///Users/xt/workspace/blog/src/content.config.ts) — 这是 frontmatter 字段的**唯一可信源**。不要靠"读一篇样例文章"来推断 schema，因为样例没用到的可选字段会被你漏掉（这就是上一版 skill 漏掉 `image`、`updated`、`category` 等字段的原因）
3. 如果路径不存在或 schema 与下方记录不符，**以 schema 为准**并提示用户 skill 文档需要更新，不要在其他位置写文件
4. **收集已有 tag 池**——用类似下面的命令把所有已发布文章的 tag 聚合起来：
   ```bash
   awk '/^tags:/{f=1;next} f&&/^  - /{print substr($0,5);next} f{f=0}' \
     /Users/xt/workspace/blog/src/content/posts/*.md | sort | uniq -c | sort -rn
   ```
   结果里每个 tag 前的数字是使用次数。拟大纲时用作**候选池**，优先复用已有 tag，真的没合适的再新建

这一步是为了防止 skill 里的事实过时后悄悄写错地方，以及防止 tag 命名漂移。

灵活调整，直到用户满意。

## 第三阶段：撰写文章

### Frontmatter 规范

> **唯一可信源是 [src/content.config.ts](file:///Users/xt/workspace/blog/src/content.config.ts) 的 zod schema**。下面是按当前 schema 整理的字段清单，schema 改了以它为准。

**必填字段**（写出即可，不写会出问题）：

```yaml
---
title: [中文标题]
published: [当前北京日期，YYYY-MM-DD]
description: [1 句话摘要，≤120 字符]
tags:
  - [tag1]
  - [tag2]
---
```

**常用可选字段**（按需启用）：

| 字段 | 类型 | 用途 | 用法说明 |
|---|---|---|---|
| `updated` | date | 更新日期 | 文章后续修订时填，YYYY-MM-DD |
| `category` | string | 分类 | 单个字符串，与 tags 区分 |
| `pinned` | boolean | 置顶 | 默认 false |
| `draft` | boolean | 草稿 | 默认 false，true 时不会发布 |
| `author` | string | 作者 | 留空走站点默认 |
| `lang` | string | 语言 | 如 `zh`、`en` |
| `comment` | boolean | 评论开关 | 默认 true |

**冷门字段**（一般不用，列在这只是知道有）：`sourceLink` / `licenseName` / `licenseUrl`（转载来源与协议）、`password` / `passwordHint`（加密文章）。

**字段填写原则**：

- **不要画蛇添足加 schema 里没有的字段**——zod 会拒绝
- **不写不需要的可选字段**——能用默认值就用默认值，frontmatter 越短越易读
- `published`：用北京时间日期，通过 `TZ='Asia/Shanghai' date +"%Y-%m-%d"` 获取（**不要用 UTC**）
- `description`：**1 句话，≤120 字符**。文章列表卡片和 SEO 摘要用的，过长会被截断
- `tags`：数量不设硬上限，按文章实际覆盖的维度来。中英文皆可，英文首字母大写（如 `CSS`、`Debug`），中文直接用（如 `小程序`）
- 文件名 = slug，决定 URL，不需要单独的 slug 字段

**tag 命名规范**（冲突时遵循，不冲突就按预检查收集到的已有写法走）：
- `JS` → 统一用 `JavaScript`
- `TS` → 统一用 `TypeScript`
- `微信小程序` → 统一用 `小程序`
- 禁用过泛的 tag：`Frontend`、`Backend`、`Dev`
- 发现新的同义词冲突时，和用户确认后追加到本列表

### 写作规范

**风格**：
- 默认使用中文撰写
- 语气自然，像是在跟同行聊技术，不要学术腔
- 开头直入主题，不要"随着 XXX 的发展"这类套话
- 结尾简洁有力，不要"总结一下/希望对你有帮助"

**结构**：
- 用 `##` 作为主要章节标题（h2），`###` 作为子标题（h3）
- 不要在文章开头重复 title（Astro 会自动渲染标题）
- 代码块标注语言类型
- 适当使用列表、表格增强可读性
- 长文章在开头可加一句话概括全文要点

**代码示例**：
- 代码要可运行，不要伪代码
- 关键代码加简短注释
- 避免超长代码块（超过 30 行考虑拆分或只展示核心部分）

**隐私脱敏（强制，不可忽略）**：

文章面向公开读者，**任何能定位到作者个人身份的信息都必须被隔离在文章内容之外**。写作与校对时强制检查：

- **绝对路径**：一律用 `~/` 或占位符，**严禁**出现 `/Users/<username>/...`、`/home/<username>/...`、`C:\Users\<username>\...`。即使在粘贴 `ls -la`、`pwd`、报错堆栈等命令输出时也必须手工替换——工具输出里带的真实路径是最常见的泄漏源
- **用户名 / 邮箱 / 真实姓名**：文章正文不出现 GitHub 用户名、Git author、邮箱、真名。引用第三方开源项目的 `user/repo` 除外（那是项目公开标识）
- **机器名、局域网 IP、端口映射**：不出现 `xxx.local`、`192.168.x.x`、`10.x.x.x` 这类私网标识
- **内部仓库 / 内部服务名**：公司内部代号、私有仓库名、内网域名一律抽象为"某个项目"、"内部服务"
- **可辨识的项目专属命名**：如果文章脱胎于私有项目，组件名、类名、文件名要通用化（参见"通用化优先"原则）

**动笔前 + 提交前各过一遍这条检查单**。写作时很容易在抄命令输出时顺手带进去，不强制校对就会漏。发现泄漏必须在 push 前修掉——已推送的仓库历史里同样算公开。

**技术诚实度（重要，常被忽略）**：

技术博客最容易翻车的地方是**把猜测写成事实**。区分三种语气，强制使用对应措辞：

| 类别 | 写法 | 反例 |
|---|---|---|
| 观察到的事实 | "实测发现…"、"在 X 环境下表现为…" | （无） |
| 基于现象的推断 | "**我的猜测是**…，没有验证源码"、"**看起来**像是…" | "X 引擎的策略是…"、"规范规定…"（除非真读过规范） |
| 引用规范/源码 | 必须给出**具体章节链接或源码位置** | "规范规定…"（不给出处） |

- **不确定就说不确定**。"看起来"、"我没读过源码"、"这是猜测"这些词不会让你显得不专业，反而提升可信度
- **不要为了行文流畅杜撰术语**（比如"收敛策略"、"锚定机制"这种听起来很懂实则模糊的词）
- 引用 CSS/HTTP/语言规范时，**要么给章节号，要么改为"按我的理解"**
- 修复方案的有效性**不要绑定在猜测的机制上**。即使机制猜错了，修复也应该独立成立

**复盘类文章的必备结构**：

凡是 bug 复盘、踩坑记、问题排查类文章，**必须包含**这几节，缺一节都是降低读者价值：

1. **现象** — 一两段，不超
2. **怎么定位到的（诊断路径）** — 这是复盘类文章的核心。完整记录走过的弯路：第一反应是什么、为什么排除、关键转折在哪一步、什么动作让范围突然缩小。读者偷的是**思路**，不是答案
3. **根因（为什么会这样）** — 注意应用上面的"诚实度"原则
4. **修复方案** — 每个修复后跟一句**副作用确认**："改了 X，原本依赖 X 的 Y 效果是否还在？为什么？"。不交代会让读者照搬时踩新坑
5. **通用经验 / 防御原则** — 抽象成可迁移的几条规则
6. **检查清单**（可选）— 与防御原则**不要重复**，要么删一个，要么让清单只放"动手前 5 秒过一遍"的快速检查项

**避免冗余包装**：
- 不要在"通用原则"和"检查清单"两个章节用不同包装说同一件事。读者会觉得在凑字数
- 写完后通读一遍：如果某条规则在两处出现，留下更具体的那一处，删另一处

**质量检查**：
- 确保技术内容准确，且区分观察 / 推断 / 引用
- 检查代码示例的正确性，确保可运行
- 确认没有前后矛盾的说法
- 文章长度适中（800-2000 字，视主题而定）
- **复盘类文章**：检查是否包含了上面 1-5 节
- **修复方案**：检查每个修复后是否交代了副作用

## 核心原则

- **先对齐再动笔** — 大纲必须经过用户确认
- **内容为王** — 技术准确性 > 文采 > 格式
- **不注水** — 宁可短小精悍，不要为了凑字数而啰嗦
- **尊重原创** — 如引用外部内容需注明来源
- **一篇一提交** — 每篇文章独立 commit，不混合其他改动
- **通用化优先** — 当文章脱胎于某个具体项目（bug 复盘、经验总结等），**禁止使用项目专属命名**（组件名、文件名、内部术语）。在大纲阶段就应该把场景抽象成通用 HTML/代码结构，并构造一个**最小复现**让任何读者能对照自己的代码。如果你写不出最小复现，说明还没真正理解通用机制
- **不写"我们项目"视角** — 文章面向陌生读者，避免"我们的 X 组件如何如何"，改为"当你有这样一段结构时"
- **诚实 > 流畅** — 不知道就说不知道，没读过源码就说没读过。技术博客的可信度是一次性资产，编一个术语就破产
- **复盘文章卖思路而非答案** — 没有"诊断路径"一节的复盘文章，价值减半。读者真正想偷的是"下次遇到类似问题怎么想"
- **修复必带副作用确认** — 每个改动后回答一句"原本依赖这个写法的 X 效果是否还在？为什么"。不交代等于让读者去踩第二个坑
- **写完通读一遍找重复** — 同一个意思如果在两节里都出现了，删掉较弱的那个。冗余是"看起来在凑字数"的根源
- **脱敏是硬约束** — 绝对路径、用户名、机器名、内部项目标识一律不得进入正文（详见"隐私脱敏"段）。粘贴命令输出时最容易漏，提交前必须单独过一遍
