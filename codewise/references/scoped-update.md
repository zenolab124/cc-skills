# 日常范围更新

适用于无参数、`update` 和局部知识维护。旧 `docs/knowledge/` 是只读参考，普通更新直接修改主仓库内已有权威文档。

## 确定范围

优先使用当前任务的明确目标、用户指定路径或提交区间。查看 Git 状态和相关 diff，区分本次与并行改动；未提交改动可作为工作区证据，但不能写成已提交事实。无明确范围且工作区干净时，询问要整理的模块或提交区间，不扫描整个项目兜底。

完整读取准备修改的文档、相关实现及必要差异，按发现扩展相邻依赖，不预先要求遍历所有代码树。历史原因不足时只检索相关会话或 Git 历史；找不到就保留未知，其他机器的完整会话不是前置条件。共享模块的影响范围遵守项目跨端确认规则。

## 选择内容与落点

- 决策：选择及原因、被否决方案的关键代价、适用条件。
- 故障经验：真实症状、触发条件、根因、有效处理；只有代码推断时明确未复现。
- 契约：消费者必须遵守的数据语义、身份、完整度、兼容性与发布边界。
- 验收：仅在确需交接时记录日期、版本、证据位置与未完成事项；上线状态使用前仍需刷新。

优先更新相关人写文档已有章节，保留人工补充；只有独立主题确实缺乏合适落点时才新建短文。不要复制整篇旧条目，不重复维护函数签名、接口计数或可以现场查出的组件介绍。规则文件仅承载用户授权的长期规则，不把每次故障扩写成全项目禁令。

若存在 `docs/PROJECT_GUIDE.md`，仅在入口变化时更新导航。旧库读取前确认当前分支与适用范围；在 linked worktree 使用主树资料时标注父分支视角，不把未合并实验写成当前实现。

## 验证与完成

检查文档引用、真实 diff 和敏感信息；仅当改变了脚本等可执行内容时运行相应定向检查。交付列明所读范围、修改位置、证据限制；没有新知识就说明零改动，不为局部文档整理运行构建或全仓测试。

范围覆盖只在本次交付中说明，不额外创建同步台账。**不得写 `docs/knowledge/_sync.json` 或任意分支的 baseline/synced_at，不写 `_meta.json`、`_branches.json`、归档或旧 INDEX，不将局部更新计作全仓同步。** 旧库缺失、归档控制状态格式错误不阻塞主仓库文档维护；若用户要求写旧库，转入显式完整/高级模式并执行原有身份、路径、锁与冲突守卫，不绕过它们。

未经用户要求不自动 commit/push。只读查询不写文件、不获取写锁、不访问远端。不要因本轮整理方便就修改其他项目的规则或启动配置。
