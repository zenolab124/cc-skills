# 三方合并协议

长功能分支合并回主线时，把 `branches/<slug>/` 的知识并进 `main/`。这是**语义三方合并**——git 只负责存历史，合并判断由 codewise 做。

## 目录

1. 为什么不是 rebuild
2. 三方合并的 base
3. 条目级合并规则

## 为什么不是 rebuild

一个 feature 分支通常只改动全部模块中的一小部分，其余条目两边完全相同——重扫它们是纯浪费。用分叉点做基准的三方合并，**AI 参与面积 = 真冲突条目数**，通常是个位数，比"丢弃状态类条目重新生成"便宜一个数量级。

前提是有 base 版本。稀疏分支目录的 `_meta.json` 里显式记录了 `forked_from`，所以 base 总是可得——这比 `merge-base` 更可靠：分叉点是**记录的**而不是**推导的**，不会被 rebase 打乱，也不存在"找不到共同祖先"的边界情况。

## 三方合并的 base

```bash
# 分支目录 _meta.json 里的 forked_from 是知识库仓库当时的 HEAD
git -C <KB> show <forked_from>:<SCOPE>/main/<条目路径>
```

取不到（条目在 fork 之后才由主线新增）→ base 视为"不存在"，走下表的"两边都新增"。

## 条目级合并规则

对 `branches/<slug>/` 里的**每个文件**（这就是本分支的全部知识贡献，无需与 main 逐条比对来找差异）：

| base | main 侧 | 分支侧 | 处理 | 需要 AI |
|---|---|---|---|---|
| 有 | 未改 | 已改 | 直接采纳分支版本 | 否 |
| 有 | 已改 | 未改 | 保持 main（分支目录里根本没这个文件） | 否 |
| 有 | 已改 | 已改 | **语义融合**：能合就合（两边各加了不同小节），矛盾则以当前代码裁决状态断言、保留双方因果断言 | 是 |
| 无 | 有同名 | 有同名 | 两边独立新增 → 送语义去重判断 | 是 |
| 无 | 无 | 有 | 直接采纳 | 否 |

`_deleted` 清单里的条目：从 `main/` 删除。**但要先确认删除理由**——若删除原因是"该 pitfall 是误判"，删；若是"这个模块在本分支被移除"，那是状态断言，须由合并后的当前代码验证，代码里模块还在就不删。

因果类条目（`pitfalls/`、`decisions/`）的合并语义是**并集**：一个坑不会因为另一条分支上没记录就不成立。只有状态类条目（`domains/`、`shared/`、`integrations/`）才可能真冲突。

## 跨路径语义去重

按路径做三方比对看不出这种重复：

```
main/pitfalls/tauri-ipc-timing.md
branches/feat-x/pitfalls/ipc-race.md     ← 同一个坑，不同文件名
```

合并后必须补一道扫描，但**不能是 N² 全库两两比对**：

1. **范围**：只扫本次合并新引入的条目，不扫全库
2. **粗筛**：对每个新条目，在 `main/` 的同类目录里找候选，命中任一条才进下一步——
   - 条目提到的文件路径有重叠
   - 条目提到的函数/类型标识符有重叠
   - 标题关键词有重叠
3. **AI 判断**：粗筛后通常只剩几对，逐对判断是否同一件事
4. **保守裁决**：判定为重复也**不自动合并**，两条都保留，写进 `<KBR>/_dedup_pending.md`

第 4 条是刻意的：**丢信息不可逆，条目重复可逆。** `_dedup_pending.md` 持久化在知识库里，用户随时可以处理；已被 dismiss 的对下次不再报告，所以清单会收敛而不是滚雪球。

## 归档

合并完成后 `branches/<slug>/` 移入 `archive/<slug>/`，保留 `_meta.json` 以便追溯"这条知识从哪个分支来"。

`archive/` **不参与任何扫描**——INDEX 生成、条目统计、互链检查都走白名单（只看 `main/` 和当前分支目录）。归档内容被当成当前知识是个静默错误，白名单从结构上排除了它。

分支被废弃而非合并时同样归档，但要在 `_meta.json` 标 `outcome: abandoned`；其中的因果断言按 [branch-resolution.md](branch-resolution.md) 的 `unmerged` + 分支已删规则处理——**"试过 X 因 Y 失败"要进 `main/decisions/` 标 `status: rejected`**，不能随目录一起归档了事。

## 触发方式

**默认被动**：分支合并回主线后，在归属分支上正常跑 `codewise update` 即可。`synced_at` 边界加合并状态判定链能处理混合场景，零心智负担。

**显式模式**：`codewise merge <branch>` 精确指定要并入的分支目录，报告里单列"从该分支并入 N 条"。适合想立刻确认某批知识已进来的时候。

两种方式走的是同一套合并逻辑，区别只在范围界定与报告粒度。
