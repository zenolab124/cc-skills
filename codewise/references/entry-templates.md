# 条目模板

六类条目的结构模板。每个条目都必须能独立被读懂，并通过“关联条目”与其他条目互链。

## 目录

1. 六分类边界
2. 六类条目模板
3. 因果类条目的溯源字段

## 六分类边界

先按问题类型分类，再套模板；文件路径或技术名相同不代表应该放在同一类：

| 分类 | 回答的问题 | 边界 |
|---|---|---|
| `domains/` | **What**：系统有哪些业务/功能域，当前如何工作 | 当前状态与职责，不承载选型原因 |
| `shared/` | **How**：跨域复用的技术机制如何实现 | 通用基础设施、公共类型/组件，不写单一业务流程 |
| `decisions/` | **Why**：为什么选 A、不选 B，后来如何演变 | 有真实权衡/被否决方案才建；不重复当前实现说明 |
| `integrations/` | **With what**：与哪个外部系统/协议交互 | 第三方服务、跨进程/跨语言边界及契约 |
| `workflows/` | **How to**：人或 Agent 要按什么步骤完成任务 | 可执行流程、顺序和验证点，不是模块架构介绍 |
| `pitfalls/` | **Watch out**：什么会失败、根因与规避是什么 | 一个独立根因一文件，不把一般注意事项硬凑成坑 |

同一主题同时有“why”和“how”时必须拆成 `decisions/` + 状态类条目并互链；否则决策演变会污染当前实现说明。作者维护的 README、AGENTS/CLAUDE 与 `docs/` 只进入 INDEX 文档导航，知识条目提炼其稳定事实和原因，不复制/改写整篇人写文档。


## domains/（功能域）

```markdown
# [功能名称]

[一句话描述这个功能域做什么]

## 架构

[文本/ASCII 架构图，展示核心组件和数据流]

## 关键文件

| 文件 | 职责 |
|------|------|
| `路径/文件名` | 一句话 |

## 核心流程

[描述主要的数据流或执行流程]

## 关联条目

- [条目名](../分类/文件名.md) — 关联原因
```

## pitfalls/（踩坑记录）

```markdown
---
confidence: confirmed | medium
evidence: session | code-only | both
---

# [陷阱主题]

**What**: [发生了什么]
**Why**: [为什么会这样]
**Action**: [怎么避免/解决]

## 关联条目

- [条目名](../分类/文件名.md) — 关联原因
```

**一个文件只写一个独立陷阱。** 若出现两个独立根因或两套独立修复姿势，拆成两个文件；同一根因的不同表现可以留在同一条目。

## 因果类条目的溯源字段

`decisions/` 与 `pitfalls/` 承载的是**代码里验证不了**的因果断言，所以必须标明这条结论有多硬、从哪来。

**confidence**

| 值 | 含义 |
|---|---|
| `confirmed` | 合并状态判定为 `merged-confirmed`（分支可达、merge commit 指名，或经完整 hash 校验的会话 commit 是当前 HEAD 祖先） |
| `medium` | 只走到文件级命中并通过内容二次验证，或只有单一会话孤证。**必须在更新报告里单列供用户确认** |

**evidence**

| 值 | 含义 |
|---|---|
| `session` | 根因来自会话记录（最有价值的情形——`git diff` 拿不到这些） |
| `code-only` | diff 覆盖但会话零覆盖：改动来自其他人或其他机器，只能从完整 commit body、PR 引用、CHANGELOG 推断。**根因很可能缺失**，更新报告要把这类模块单列出来，提示去问对应作者 |
| `both` | 代码与会话互相印证，置信度最高 |

**status**（仅 `decisions/`）

| 值 | 含义 |
|---|---|
| `current` | 当前有效的决策 |
| `superseded` | 已被后续决策取代，保留作演变记录 |
| `rejected` | 被否决的方案。**分支已删除且未合并的实验，其因果结论归到这里**——"试过 X，因为 Y 失败了"是真知识，不该因为代码没留下就丢掉 |

多个独立会话印证同一根因 → 可升到 `confirmed`；只在一处出现的孤证下调为 `medium`，不要直接丢弃。
