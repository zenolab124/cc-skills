# 迭代需求文档（PRD）

为一次迭代产出一份结构化、可校验的需求文档。文档作为开发会话与测试会话两条独立链路的**唯一事实源**——开发按 PRD 写代码，测试按 PRD 写用例，两边互不参照，最后用测试反向验证实现是否符合 PRD。

## 任务输入

$ARGUMENTS

---

## Phase 0：意图识别

解析 `$ARGUMENTS`，判断子命令：

- `new [版本号] [主题]` → 创建新 PRD（走 Phase A）
- `update [版本号]` → 修订指定 PRD，省略版本号则默认最新（走 Phase B）
- `list` → 列出所有 PRD（走 Phase C）
- 空参数或意图不明 → 主动追问用户："你想新建一份 PRD、修订现有 PRD，还是查看列表？"

**禁止**：擅自决定子命令。如果 `$ARGUMENTS` 只有版本号没有动词（比如只输入 `v3`），追问是 new 还是 update。

---

## 通用前置检查

无论哪个子命令，先执行：

1. 确认当前工作目录（项目根）。如果用户在子项目里，PRD 应放该子项目的 `docs/prd/` 下，不要写到外层
2. `ls docs/prd/ 2>/dev/null` —— 看现有 PRD 列表，建立基线
3. 如果 `docs/prd/` 不存在，**不要立即创建**——等到真的要写文件时再创建，避免空目录

---

## Phase A：新建 PRD（`new`）

### A.1 收集元数据

按顺序追问（**一次只问 1-2 个，不要轰炸**）：

1. **版本号**：
   - 如果已有 PRD，列出最近 3 份的版本号风格作为参考
   - 用户可用任何风格：`v1` / `v1.0.0` / `v2026-05-login` / `sprint-23`...
   - Skill 不解析版本号语义，只把它当成文件名标签
   - 如果用户没主意，根据已有风格给出建议（"沿用之前的 vN 风格的话，下一个是 v4"）

2. **主题**（slug）：
   - 用 kebab-case 英文短语，作为文件名一部分
   - 例：`login-redesign`、`payment-refund`、`onboarding-v2`
   - 如果用户给中文，主动建议英文 slug

3. **背景**（1-3 句话）：
   - 为什么做这一版？要解决什么问题？
   - 这一段的目的是给未来的 AI/人理解决策动机，不写"为什么"日后看不懂

### A.2 框定范围

先框范围、再谈细节，避免 AI 在功能点讨论时不断引入新需求：

4. **In Scope**：本版要做哪些事？（高层粒度，3-8 条即可）
5. **Out of Scope**：明确**不做**的事——这是给 AI 划红线，比 In Scope 更重要

> 追问技巧：用户说完 In Scope 后，主动反问"是否考虑过 X？要不要做？"，逼出更明确的 Out of Scope。

### A.3 全局约束

6. **全局约束**：横切的约束条件——
   - 命名规范？（API 命名、变量命名、文件命名）
   - 错误处理统一约定？（错误码体系、报错文案规范）
   - 技术栈限制？（必须用某框架/库；禁止某依赖）
   - UI 风格？（设计系统、深色模式、响应式断点）
   - 性能/兼容性硬指标？

如果没有横切约束，明确写"无"，不要留空让 AI 猜。

### A.4 逐条收集功能需求

每个 FR **逐条**走完整模板，不要让用户一次描述完所有 FR：

对每个 FR 追问：
- **FR-ID**：自动递增 FR-001、FR-002...
- **功能名**：一句话概括
- **优先级**：P0（必做）/ P1（应做）/ P2（可选）
- **描述**：1-2 句话说清要做什么
- **前置依赖**：依赖其他 FR？依赖外部系统/已有模块？
- **验收标准**（Given-When-Then 格式，至少覆盖：1 个正常路径 + 1 个边界 + 1 个错误路径）
- **边界与备注**：特别提醒（"不要 X"、"注意 Y"），用来约束 AI 不自由发挥

> **强制追问**：每个 FR 收集完后，必须问"边界条件想全了吗？错误路径呢？空状态呢？" 这是 PRD 当护栏的关键——AI 实现时遇到没明示的边界容易乱发挥。

### A.5 非功能需求（可选）

如果有性能、安全、可访问性、可观测性等横切要求，按 NFR-001、NFR-002 类似 FR 格式收集。没有就跳过。

### A.6 生成文件

文件路径：`docs/prd/<版本号>-<主题>.md`

按下方"PRD 文件结构"模板写入。frontmatter 的 `created` 和 `updated` 都用今天日期（北京时间，`TZ='Asia/Shanghai' date +"%Y-%m-%d"`）。

### A.7 自检清单（强制，不可跳过）

文件写入后，**自己**通读一遍，逐项核对：

- [ ] **每条 FR 都有验收标准**，且至少包含正常/边界/错误三类至少各一条
- [ ] **每条 FR 都有"边界与备注"**——空就明确写"无"，禁止留空（留空 = AI 实现时自由发挥的入口）
- [ ] **Out of Scope 段不为空**——至少一条。如果真的全是 In Scope，主动反问用户"是否考虑过 X 也属于本版？是 In 还是 Out？"
- [ ] **全局约束**每一项都明确写了内容或"无"，没有遗漏的横切维度
- [ ] **依赖关系自洽**——FR-A 标注依赖 FR-B 时，FR-B 必须真实存在；不存在就提示用户补
- [ ] **没有模糊措辞**——全文搜索"等"、"等等"、"相关"、"合适的"、"合理的"、"友好的"、"较好"、"等等场景"，找到一处就要么改具体要么删掉。这些词是 PRD 的"AI 自由发挥触发器"
- [ ] **没有"以后再说""待定"等占位**——PRD 是工单，未确定的事项要么明确写到 Out of Scope，要么本轮直接定下来

发现任一项不通过，**主动追问用户补**，不要自己脑补填。补完后再次自检直到全通过，才告知用户文件路径。

### A.8 交付告知

通过自检后，告诉用户：
- 文件路径
- 自检中**追问并补全的内容**清单（让用户知道做了哪些"主动补强"，方便复核）
- 提醒"开发会话用 `@docs/prd/<文件名>` 加载，测试会话同理"
- 提醒"开发期间需求变了用 `/prd update`，开下一轮迭代用 `/prd new`"

## Phase B：修订 PRD（`update`）

### B.1 定位目标版本

- 如果 `$ARGUMENTS` 给了版本号，找对应文件
- 如果没给，默认最新（按 git 提交时间排序，最新一份）。如果不是 git 仓库，按 mtime
- 找不到对应文件，列出现有 PRD 让用户选

### B.2 关键判断：补漏 vs 新需求

**这是修订流程最关键的一步**，主动追问用户：

> "你这次要改的内容，是哪一类？
> A. 补漏/纠错——当时就该写但没写、或当时理解有偏差（→ 改这个 PRD 合理）
> B. 新需求——基于现有功能提出的新变更（→ 建议开新版 vN+1，避免污染历史 PRD 的语义）
> C. 大改重做——旧功能彻底重做（→ 建议开新版，旧 PRD 标注「被 vN+1 替代」）"

如果是 B 或 C，**主动建议改用 `/prd new`**，不要默认帮用户改旧 PRD。

### B.3 收集变更

用户确认是补漏后，追问要改什么：
- 新增 FR？（按 A.4 流程）
- 修改 FR？（指明 FR-ID，描述改动）
- 删除 FR？（指明 FR-ID，记录删除原因）
- 调整 scope？
- 调整全局约束？

### B.4 应用变更

- 直接修改原文件
- **在「修订记录」段追加一条**：
  ```
  - YYYY-MM-DD 修订：<改了什么、为什么>
  ```
- 更新 frontmatter 的 `updated` 字段为今天
- 不要生成新文件，不要保留旧版本快照（git 已经在做版本控制）

### B.5 提醒下游

修改完后告诉用户：
- 哪些 FR 受影响
- 提醒"如果开发会话已经按旧版做了，需要回去补做或调整"
- 提醒"测试用例可能也需要同步"

## PRD 文件结构（模板）

```markdown
---
version: <版本号>
title: <主题>
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

# <版本号> - <主题>

## 修订记录

- YYYY-MM-DD 创建
- YYYY-MM-DD 修订：<内容>（如有）

## 背景

<1-3 句话说明这一版要解决的问题与动机>

## 范围

### In Scope
- <要做的事 1>
- <要做的事 2>

### Out of Scope
- <明确不做的事 1>
- <明确不做的事 2>

## 全局约束

- **命名**：<规范或「无」>
- **错误处理**:<约定或「无」>
- **技术栈**:<限制或「无」>
- **UI/UX**:<风格或「无」>
- **性能/兼容性**:<硬指标或「无」>

## 功能需求

### FR-001: <功能名>

- **优先级**：P0
- **描述**：<1-2 句话>
- **前置依赖**：<FR-XXX 或外部模块，无则写「无」>

**验收标准**：
- Given <前置> When <动作> Then <结果>（正常路径）
- Given <前置> When <动作> Then <结果>（边界）
- Given <前置> When <动作> Then <结果>（错误路径）

**边界与备注**：
- <特别提醒，避免 AI 自由发挥的事项>

---

### FR-002: <功能名>

...

## 非功能需求（可选）

### NFR-001: <性能/安全/可访问性等>

- **类别**：性能 / 安全 / 可访问性 / 可观测性 / 其他
- **要求**：<具体描述与可校验的指标>
```

## 核心原则

- **PRD 是给 AI 当护栏，不是给人读的产品故事书** —— 结构化、可校验、无歧义优先于文采
- **禁用模糊措辞** —— PRD 全文不得出现"等"、"等等"、"相关"、"合适的"、"合理的"、"友好的"、"较好"、"良好的"、"必要时"这类模糊词。这些词是 AI 自由发挥的触发器：看到"友好提示"会自己编文案，看到"合理重试"会自己定次数。每条要求要么写具体值/具体规则，要么明确写"由开发自行决定"
- **每条 FR 必须有可机读的验收标准** —— Given-When-Then 格式，让测试会话能直接派生用例
- **Out of Scope 比 In Scope 更重要** —— AI 的自由发挥最容易在没明示的边界失控
- **每条 FR 必带边界条件** —— 收集时强制追问"边界、空状态、错误路径"
- **修订原地改 + 修订记录** —— Git 已经在做版本控制，不再用文件名做二次版本管理
- **新需求开新版，补漏改旧版** —— Skill 在 update 时主动追问，避免污染 PRD 语义
- **不假设版本号格式** —— `vN` / `vN.M.P` / 日期 / 自定义都支持，用户决定
- **不替用户做产品决策** —— Skill 只负责把决策**结构化记录**下来，不主动建议"应该做什么功能"
- **一份 PRD 描述一轮迭代** —— 不试图在一份 PRD 里覆盖整个产品，那是产品文档的事，本 Skill 不做
- **不维护产品文档** —— 产品当前状态由代码本身 + codewise 知识库提供；PRD 只管"本轮变更"
