# cross-talk — 跨项目 Agent 协作

让两个各自扎根不同代码库的 Agent，通过多轮协商产出共同产物。你（Claude）做编排层，用户随时可介入。

## 输入

`$ARGUMENTS` 格式：`<other-project-path> [topic]`

- `other-project-path`：另一个项目的路径（必须）
- `topic`：协商主题（可选，省略则追问）

当前工作目录即为"本方项目"。

## Phase 0：解析与校验

1. 从 `$ARGUMENTS` 提取路径和主题
2. 路径校验：`ls <path>` 确认存在。支持 `~` 展开。如果找不到，列出可能的候选（`ls` 父目录）让用户选
3. 如果没给 topic，追问："这次协作要产出什么？比如 API 契约、集成方案、共享数据结构……"
4. 确认两个项目身份后，给每个项目取一个**简短代号**（从目录名推导，如 `cc-space`、`inkast`），后续对话中用代号指代

## Phase 1：项目探查

并行派出两个 Agent（用 Agent 工具），各自探查一个项目：

**Agent A（本方）prompt 模板**：
```
你是「{代号A}」项目的代表。你的任务是为即将到来的跨项目协商准备己方上下文。

协商主题：{topic}

探查策略（按优先级）：
1. 先读项目根目录的 CLAUDE.md（如有）
2. 再读 docs/knowledge/（codewise 知识库，如有），优先看 overview 和与主题相关的模块文档
3. 以上不足以覆盖主题时，再用 Explore 补充扫描相关代码

请产出以下信息：
1. 项目概述（一句话）
2. 与协商主题相关的现有架构/接口/模块（具体文件路径 + 关键签名）
3. 己方的约束和偏好（技术栈、命名风格、通信协议偏好等）
4. 己方对这次协作的诉求（需要对方提供什么？期望什么形式？）

只输出结构化摘要，不要输出代码块。保持简洁，每项 3-5 句话。
```

**Agent B（对方）** 同理，cwd 指向对方项目路径。

**注意**：如果对方项目路径是当前项目的子目录或同目录，直接读取即可，不需要特殊处理。如果是完全不同的路径，Agent 需要用绝对路径访问。

两个 Agent 返回后，向用户呈现双方摘要，格式：

```
📋 项目探查完成

【{代号A}】
{Agent A 摘要}

【{代号B}】
{Agent B 摘要}
```

追问用户："双方上下文准确吗？有什么要补充或修正的？确认后开始协商。协商过程中你想每轮过目，还是让它们自己跑、关键节点再找你？"

用户的回答决定 Phase 2 的**介入模式**：
- **每轮介入**（默认）：每轮结束暂停，用户选继续/介入/终止
- **自动模式**：Agent 自行跑完所有轮次，仅在达成共识或触达上限时暂停。用户在 Phase 1 确认时明确说了"不用每次确认"、"自己跑"、"自动"等意思即视为选择此模式

## Phase 2：多轮协商

每轮协商包含两步：一方提案/回应 → 另一方回应。第一轮由与主题关系更密切的一方先发（通常是"需要提供能力的一方"先出方案）。

### 单轮流程

**Step 1 — 发起方 Agent**：

派出 Agent，prompt 包含：
- 己方项目上下文（Phase 1 摘要）
- 对方项目上下文（Phase 1 摘要）
- 协商主题
- 上一轮对方的回应（首轮无）
- 用户的介入意见（如有）
- 指令："基于以上信息，提出/修改你的方案。明确列出：(1) 具体提案内容 (2) 对对方上一轮回应的采纳/反驳 (3) 仍需对方确认的问题。如果你认为双方已达成共识，明确声明'共识已达成'并输出最终方案。注意：你代表己方项目的利益，基于己方的实际技术约束做判断。不要为了礼貌或求速而让步——只在对方方案确实更优、且不违反己方约束时才同意。"

**Step 2 — 回应方 Agent**：

派出 Agent，prompt 包含相同上下文 + Step 1 的输出，指令："审阅对方提案，回应：(1) 同意的部分 (2) 需要修改的部分及理由 (3) 你的反提案或修改建议。如果完全同意，声明'共识已达成'。注意：你代表己方项目的利益，基于己方的实际技术约束做判断。不要为了礼貌或求速而让步——只在对方方案确实更优、且不违反己方约束时才同意。"

### 轮间处理

每轮结束后，向用户呈现本轮结果：

```
🔄 第 N 轮协商完成

【{发起方代号}提案】
{要点摘要，3-5 行}

【{回应方代号}回应】
{要点摘要，3-5 行}

状态：{双方是否趋向共识 / 仍有分歧点}
```

**每轮介入模式**下，问用户三选一：
- **继续** — 自动进入下一轮
- **介入** — 用户给出指导意见，注入下一轮的 prompt
- **终止** — 用户认为够了，直接进入合成阶段

**自动模式**下，跳过用户确认，直接进入下一轮。但仍然向用户输出每轮的简要状态行（一句话），让用户知道进度。

### 收敛判断

以下任一条件触发自动进入 Phase 3：
- 双方 Agent 都在同一轮声明"共识已达成"
- 达到 8 轮上限（告知用户"已达轮次上限，基于当前最佳状态合成产出"）

## Phase 3：合成产出

派出一个 Agent，输入所有轮次的协商记录，指令：

```
你是跨项目协商的记录员。基于以下多轮协商记录，产出最终协商成果。

协商主题：{topic}
参与方：{代号A}（{项目路径A}）、{代号B}（{项目路径B}）

{所有轮次记录}

请产出：
1. 协商结论摘要（双方达成的共识要点）
2. 具体产物（根据主题类型产出对应内容，如 API 契约则输出接口定义，集成方案则输出步骤清单）
3. 各方待办（{代号A} 需要做什么、{代号B} 需要做什么）
4. 未决事项（如有分歧未解，列出）

格式要求：产出要可直接复制到两个项目中使用。
```

将合成结果写入当前项目的 `docs/cross-talk/{date}-{topic-slug}.md`。

向用户呈现产出摘要和文件路径，提醒：
- "协商记录已保存到 {文件路径}"
- "各方待办已列出，可以分别在对应项目中执行"

## 关键原则

- **编排层不做决策** — 你只传递、格式化、催促收敛，不替任何一方做技术判断
- **上下文隔离** — 每个 Agent 只在己方项目里探查，不跨项目读代码（通过摘要交换信息）
- **用户是最终裁判** — 每轮都给用户介入机会，任何一方的方案都可以被用户否决
- **摘要不代码** — 轮间呈现给用户的是摘要，不是大段代码。用户要看细节再展开
- **收敛优先** — Agent 的 prompt 始终引导向共识，不鼓励无限争论
